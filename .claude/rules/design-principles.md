# 설계 원칙

> **계층 간 책임을 명확히 분리하고, 인터페이스는 간결하게 유지하라.**

## 핵심: 계층 분리와 추상화

Spring의 Controller → Service → Client/Repository 계층은 단순한 폴더 구분이 아니다.
각 계층이 자신의 책임만 갖고, 하위 구현을 노출하지 않아야 한다.

- **Controller**: HTTP 요청/응답 변환만. 비즈니스 로직 금지.
- **Service**: 비즈니스 로직 집중. 인프라 세부사항(HTTP, DB 쿼리)을 몰라야 한다.
- **Client/Repository**: 외부 시스템 통신. Service가 어떻게 쓰는지 몰라야 한다.

계층을 건너뛰지 마라 (Controller → Repository 직접 호출 금지).
순환 참조를 만들지 마라 (Service A ↔ Service B).

## 좋은 인터페이스

- 메서드 이름은 **무엇을 하는지** 설명한다 (어떻게가 아니라).
- 파라미터는 호출자가 알아야 할 최소한만 요구한다.
- 반환 타입은 호출자가 필요한 것만 포함한다 (Entity를 그대로 반환하지 마라).
- Ubiquitous Language: 도메인 용어를 코드에 일관되게 반영한다.

## 최적 복잡도

오컴의 면도날. 단순할수록 견고하다.

- 지금 필요하지 않은 추상화를 만들지 마라.
- 비슷한 코드 3줄이 섣부른 추상화 1개보다 낫다.
- 설정 가능하게 만들지 마라 — 바꿔라.
- 인터페이스가 소비되는 방향으로 복잡도가 줄어야 올바른 설계다.
